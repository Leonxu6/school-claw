# Lessons

Record user corrections here so future work avoids repeating the same mistake.

## Active Lessons

- When drafting issues for this repo, make every issue self-contained for a fresh agent window. Do not rely on prior conversation context; include working directory, required docs to read, project summary, non-negotiable architecture constraints, concrete deliverables, and verification expectations in the issue body itself.
- For CLAW planning, do not confuse scenario validation with scenario-specific implementation. CLAW is one OpenClaw-based education agent with general capabilities; issues should build reusable platform/data/scope/MCP/agent capabilities, then use product scenarios only as acceptance tests. Always include OpenClaw source checkout and API/runtime verification as a prerequisite capability track.
- When starting a dispatched issue that is blocked by an earlier issue, inspect the completed dependency branch or worktree first and carry forward its recorded understanding before creating the new worktree or implementation plan.
- When delivering an issue implementation, state the acceptance standard first: what capability was built, what exact loop proves it, which commands the user should run, and what output means PASS. Do not leave the user to infer closure from a file/change list.
- For OpenClaw integration issues, a local deterministic harness is not enough unless the spec explicitly allows simulation. The acceptance loop must exercise the real OpenClaw-facing boundary named in the issue, including runnable MCP server paths and evidence that tool calls passed through that boundary.
- For scoped file listing, apply the same realpath/symlink escape checks as file reading before parsing any candidate Markdown. Never parse title/excerpt metadata from a path until the candidate's real path is proven inside the archive and inside the requested read root.
- For scoped file reading, lexical `fileId` authorization is only a first gate. After `realpath`, verify the real target is still inside the current scope's canonical `readRoots`; being inside `dataRoot` is not enough because a symlink can point from an allowed student directory to another student's file.
- Before calling an issue done, check `git status --untracked-files=all` and ensure all intended implementation, tests, fixtures, scripts, and issue specs are tracked or intentionally ignored. Do not let core deliverables remain untracked.
- Passing tests is not enough for delivery: verify the branch `HEAD` contains the issue implementation/spec, not just the worktree. If the user expects a mergeable handoff, stage and commit the tracked deliverables before calling the issue complete.
- If an API accepts filters such as `dateFrom`, `dateTo`, or `query`, either implement them with tests or reject unsupported usage explicitly. Never silently ignore a narrowing filter.
- Before implementing a dispatched issue, create or enter the matching `/Users/leon/school-claw-worktrees/<issue-name>` worktree and verify the branch with `git status -sb`. Do not implement issue code in the planning/main workspace.
- Do not make GitHub Actions depend on local-only sibling checkouts such as `/Users/leon/openclaw`. External checkout integration tests must either set up that checkout in CI or explicitly skip with a clear availability guard.
- For write primitives, `writeRoots` authorization is necessary but not sufficient. Also bind each target kind to the correct role/capability so source-provenance files such as `parent-observations` cannot be written by teacher scopes.
- For “no write without audit,” regression-test audit storage failure explicitly. Preflight the audit target before changing business files, so an unavailable `audit/` path cannot leave unaudited archive mutations.
- When a branch is based on an older dependency worktree, copy the current issue spec into `tasks/issues/` before delivery so fresh agents and reviewers do not validate against stale numbered issue files.
- Before developing a numbered issue, verify the target Git repository and issue source first. Do not infer from a similarly named directory or upstream repo; for school-claw issue work, use `/Users/leon/school-claw` and its tracker/files.
- For tool-call request fields that are TypeScript unions, add runtime validation and regression tests with invalid JSON values. MCP/runtime callers can pass strings such as `"upsert"` even when TypeScript says the mode is only `"create" | "replace"`.
- For audit preflight, checking that `audit/` is a directory is not enough. Probe the exact audit parent directory with a real write/delete before changing business files, and regression-test an unwritable `audit/YYYY-MM` directory.
- When the user asks to continue a numbered issue, pause implementation until the matching `/Users/leon/school-claw-worktrees/<issue-name>` worktree exists and is checked out; if the current directory is only planning docs or another workspace, create/enter the issue worktree first.
- For artifact provenance, validating that the creator can read `sourceFileIds` is not enough. For student-targeted artifacts, every source must also be safe for that target student's audience; never let a teacher create a student artifact whose metadata or content points at another student's archive.
- For "no artifact without audit," audit preflight alone is not enough. Any artifact primitive that writes the business file before audit append must have a regression-tested rollback/compensation path for audit append failure.
- For feature review, passing unit/integration commands is not enough. Add a user-journey E2E check from the external entry point through the visible response, and verify the output from the user's perspective before calling an issue complete.
- When a verifier says behavior passes but delivery state fails, fix delivery hygiene before re-reporting: remove `??` core files by staging/committing them, and ensure the matching numbered issue spec exists in the issue worktree.
- For `claw-agent` capability work, do not substitute a handwritten deterministic TypeScript agent loop for OpenClaw Pi Runtime. `claw-agent` means the agent running under OpenClaw runtime; demos/tests for agent behavior must exercise the OpenClaw runtime or the closest source-supported QA-channel runtime boundary.
- For OpenClaw Pi Runtime MCP tool paths, never let model-provided `ssid` reach the CLAW MCP server as authority. The Scope Bridge must run at the final tool-execution boundary, overwrite `ssid` from the trusted OpenClaw `sessionKey`, and include a forged-`ssid` E2E regression probe.
- OpenClaw runtime E2E tests depend on an external pinned OpenClaw checkout. Guard that availability explicitly and skip with intent in generic CI instead of letting Node surface misleading `spawn pnpm ENOENT` from a missing `cwd`.
- When debugging Codex App project settings, do not trust basename-only UI labels such as `school-claw`. Check every same-named directory with the App's own Codex binary and configure the exact cwd the UI is listing.
- Keep quality gates and PR publishing as separate responsibilities. The Stop hook runs reviewer and verifier in parallel, then calls TPR after both pass; standalone `$ship-pr`/`$tpr` should publish only and must not duplicate reviewer/verifier gate execution.
- Keep the Codex Stop-hook quality gate simple: reviewer and verifier are two independent read-only gates that run in parallel; any failure blocks for the main agent to fix; TPR runs only after both pass. Do not reintroduce sequential reviewer/verifier latches unless the user explicitly asks.
- Reviewer/verifier quality gates must be mechanically read-only, not just prompted to behave. Run Codex gates with `--sandbox read-only`, run reviewer/verifier in isolated workspaces, and skip full Stop-hook gates for subagent/explorer sessions so only the main agent fixes and publishes.
- Do not block a quality gate solely because the project diff changed while the gate was running. Git is only for detecting the current diff/hash and latch keys; reviewer/verifier pass/fail must come from their findings and verification evidence.
- TPR PR descriptions are for human review first, not code archaeology. Lead with plain-language sections: what changed, task completion, E2E/acceptance tests and results, current implementation status, technical architecture status, and risks; move commit/file details to an appendix.
- If a quality gate finds a problem, it must write findings to its JSON/text output only. It should never "helpfully" repair code, docs, tests, formatting, snapshots, or git state; the main agent reads the findings and applies any repository edits in the main thread.
- For pinned OpenClaw integration validation, do not run `pnpm --dir /Users/leon/openclaw exec openclaw`; it can resolve a global binary. Invoke `/Users/leon/openclaw/src/entry.ts` through `tsx`, or import the pinned source validator directly.
- Shipped OpenClaw config files must be checkout-relative, not hardcoded to `/Users/leon/school-claw`. Validation must run from the current checkout root and fail if local plugin/MCP assets are missing, so it cannot pass by loading stale files from another workspace.
- OpenClaw's real session-spawn tool id is `sessions_spawn`, not `session_spawn`. Deny `sessions_spawn`, `sessions_yield`, and `subagents` when the product requirement says session-spawn/subagent-style native tools are unavailable.
- In sandboxed gates, do not launch TypeScript OpenClaw helpers through the `tsx` CLI; it opens an IPC socket and can fail with `listen EPERM`. Use `node --import <checkout>/node_modules/tsx/dist/esm/index.mjs ...` for verifier-facing E2E/helper paths.
- OpenClaw verifier-facing E2E tests must not skip critical user journeys just because the sandbox cannot bind `127.0.0.1`. Move deterministic model/QA-bus fixtures in-process when possible, while still exercising the real OpenClaw Pi Runtime, Scope Bridge, and CLAW MCP boundaries.
- Quality gates must evaluate the real PR delivery surface, not only dirty working-tree files. Include committed `base...HEAD` branch diff plus staged/unstaged changes in reviewer/verifier prompts, and infer the active issue from branch numbers such as `codex10` when `tasks/todo.md` is absent.
- For OpenClaw config fields named like `systemPromptOverride`, verify whether the runtime expects prompt text or a file path from source behavior, not from naming intuition. Add tests that assert the runtime config contains the actual prompt rules, not only a readable local path.
- OpenClaw integration plugins that live inside this repo must cold-import from the repo without relying on bare `openclaw/*` package resolution or tsx cache. Put shared logic in repo-local modules and have the plugin export a plain plugin object that OpenClaw can load.
- Model-facing MCP schemas must not require trusted session identifiers such as `ssid` when a runtime bridge is responsible for injecting them. Keep backend scope enforcement mandatory, but expose optional `ssid` in tool schemas and regression-test listTools output plus bridged calls.
- Prompt/workspace contracts need per-rule traceability, not aggregate section buckets. Map each behavior rule such as scope-first, evidence reads, sedimentation, artifacts, refusal/safety, and tone to the concrete PRD and architecture sections it satisfies.
- If an OpenClaw `systemPromptOverride` is used, it must contain the full behavior contract the agent needs at runtime. Do not rely on a denied native file tool or an unproven workspace bootstrap path to read `AGENTS.md`; regression-test the shipped config prompt content.
- When the user says a numbered local issue exists, inspect the exact `tasks/issues/<number>-*.md` file before asking broader sequencing questions. If corrected to a specific number, pivot to that issue and record any prerequisite gaps as part of the target issue plan.
- Stop-hook quality gates are task-level gates, not diff-level gates, when the user asks for speed. Once reviewer or verifier passes for a task, persist a pass latch and do not rerun that gate just because files changed; only rerun unpassed gates or when `QUALITY_GATE_FORCE=1` is set.
